    How it's built

    Three stages — pre-call, the call, post-call — and a write-back at the end that an idempotent call_id key makes safe to re-run.

    The three stages

    Stage 1 · Pre-call

    Suppression and priority

    Pure code, no LLM, costs nothing to run — and the part of the product that does the most work before anyone picks up a phone.

    • Skip calling if: already paid, a dispute is open, an active promise hasn't come due, the contact opted out or is wrong-party, inside the cooldown window, outside calling hours, or the bucket is 90+ (routed to a human).
    • Every suppression is logged with a reason — "calls we correctly didn't make" is tracked as its own metric.
    • What's left is scored: priority = balance_weight × bucket_weight × ptp_broken_escalation × contactability. A broken promise escalates priority, it doesn't discount it.
    • Output is a context pack: contact, invoices, total outstanding, prior promises and whether they were kept, open disputes, last contact, preferred language.
    Stage 2 · The call

    Deterministic where it matters

    Model-driven only in phrasing and branch detection — everything that must never vary is hard-coded instead.

    • Disclosure and the authority check are one fixed opening line, spoken before the model runs at all — never reworded, never skipped, never asked twice.
    • Hard 3-minute cap. No amount is ever spoken that isn't already in the context pack.
    • Works exactly one invoice — the most overdue — to a complete outcome, and books a callback for any others instead of racing the clock across all of them.
    Stage 3 · Post-call

    Five specialists, then a supervisor

    Once the call ends, five typed extractors run in parallel against the transcript:

    • Outcome — structured result, reason code, next action.
    • Promise validation — complete, future-dated, within the outstanding balance, valid method. Computed in code from the extraction, never judged by the model.
    • Dispute — reason code, invoice, routing target.
    • Compliance & QA — disclosure, authority, permitted statements, discounts/threats, a misstated total.
    • Summary — a plain 2–3 sentence recap, purely descriptive.

    A supervisor merges all five. Anything below the confidence threshold, or any hard compliance violation, is held for human review instead of auto-written — regardless of how confident everything else felt.

    The data path

    Pre-call AR sheet → suppression → priority → context pack
    The call Vapi · disclosure → authority → one invoice to resolution
    Post-call 5 specialists in parallel → supervisor merge
    Write-back Call log, PTP register, disputes, exceptions — Sheets as the CRM

    Every write is keyed on call_id, so re-running an analysis on the same call never duplicates a row — it reconciles the old one instead (see "What I learned").

    Design decisions worth defending

    Deterministic in-call, orchestrated after

    The call's non-negotiables — disclosure, authority, the 3-minute cap, never speaking a number outside the context pack — are hard-coded, not left to a model to remember mid-conversation. A prompt instruction can be silently weakened by a later refactor (see "What I learned"); a structural guarantee can't. Post-call is the opposite on purpose: five LLM specialists reading the transcript in parallel, because judgment and extraction over unstructured text is exactly what a model is good at. The model's read is trusted for extraction, never for the final word — a confidence gate and a set of hard-violation overrides decide whether anything actually gets written.

    One invoice per call

    Early builds walked every open invoice in one call and raised the duration cap when it ran out of time. That only relocated the failure — any fixed cap eventually runs out against a chattier customer or a third invoice. The agent now resolves exactly one invoice — the most overdue — to a complete outcome and books a callback for the rest. It also matches how collections actually works: one clean resolution plus a booked callback beats several rushed, half-finished commitments squeezed into one call.

    90+ days overdue is never automated

    Accounts in the 90+ bucket are routed to a human, full stop. This is a product decision, not a technical limitation — those conversations carry legal and relationship risk an automated caller shouldn't be taking on.

    Why the caps and the replay fallback exist

    This demo runs against a small, finite Vapi balance, not a production account. Every live call is checked server-side — a spend floor, a daily ceiling, a one-call-per-visitor window — before the browser is ever handed a working call configuration; it never receives a usable key for a call that isn't actually allowed. A visitor who's capped out doesn't hit a dead button: the page falls back to replaying a real saved call through the exact same pipeline instead, so the system is still demonstrated honestly — on recorded input rather than their own voice — rather than just failing closed.

    Evals

    Specialist agreement with a human labeller, on the only real transcripts this project has. n = 9.

    What this is, and isn't

    This eval runs the real post-call pipeline against the nine saved calls in fixtures/raw/ and reports how often it agrees with one person's independent judgement of the same calls. That is the entire scope. It is not:

    • a kept rate — not enough call volume for one to mean anything
    • an accuracy estimate at production volume
    • a claim about real-world performance — most of these nine calls are synthetic test calls against a fake dataset, not real customers

    Read it as exactly what it is: on nine calls, did the pipeline's judgement match a human's.

    Before this, the only thing checking the five specialists was the unit test suite — which checks code behaviour given a fixed, hand-written input, not whether a specialist's judgement on a real transcript is correct. Nothing measured specialist judgement against ground truth until this.

    Method

    1 Labeling (label-calls) — one saved call at a time, full transcript and tool calls, judged independently on: outcome type, whether a promise was captured and whether it was complete (amount, date, method, future-dated, within the outstanding balance, valid method), whether a dispute existed, whether any compliance rule was actually broken, and whether the call should have been auto-written or held for review. Labels save immediately per call, resumable, with no pipeline output ever shown while labeling.
    2 Comparison (run-eval) — for every labeled call, runs the real pipeline (the same function the live and replay paths use, not a separate eval-only code path) and compares its output to the label on each dimension. Cached per call so re-running the report doesn't re-spend OpenAI credit.
    3 Report — per-specialist agreement (count and percentage per judged dimension); write-decision accuracy split by direction — false holds (should have auto-written, pipeline held it) versus false writes (should have been held, pipeline auto-wrote it — the more dangerous direction); and every disagreement in full, not just the percentage.

    Field-mapping notes: "promise complete" is scored only on calls where a promise was captured at all, against has_promise and not downgraded_to_soft_commitment. "Compliance violated" uses the exact same hard-violation test the supervisor itself uses to gate write-back — a low QA score alone, with no hard violation, doesn't count. Four of the nine calls belong to an account reassigned when the fake dataset was regenerated; their account facts are recovered from the call's own embedded system prompt rather than a live Sheet row.

    What I learned

    From docs/FAILURES.md — real incidents hit during manual testing, kept separate from the design doc because these are things that actually happened, not things planned for.

    Three worth leading with

    2026-09-30

    An invoice-hyphen bug, silently downgrading valid promises

    Building the demo's replay mode meant pushing a real saved call through the real pipeline for the first time, instead of hand-written example data. The first real call landed in the exception queue looking like a genuine problem: a complete, correctly-recorded, in-full promise came back amount_within_outstanding=false and downgraded to a soft commitment.

    Cause: the agent sometimes reads an invoice number back with an inserted hyphen — the transcript has the agent saying "invoice US-CS/26-27/0002," but the Sheet's own invoice_number for that invoice is USCS/26-27/0002, no hyphen. The matching code compared these with exact string equality, so the promise validator could never find the invoice and defaulted to "not within outstanding." A hardcoded demo fixture, written to already match, could never have exposed this — only real data, pushed through the real matching code, did.

    Fix: strip every non-alphanumeric character and uppercase both sides before comparing invoice references. Punctuation an invoice number picks up in transit no longer breaks a match the digits and letters otherwise confirm.

    Replay mode wasn't just a demo feature — it was the first thing in this project to run real saved data through real matching code instead of fixtures written to already pass.
    2026-09-17

    Two prompt regressions that ~280 passing tests missed

    Two real call defects, found the same day on a validation call: (1) the agent asked "what amount, when, and how" as one bundled turn, despite an explicit one-question-per-turn rule — because two other prompt sections, worded more specifically and sitting closer to the model's decision point, contradicted that rule with a compact conjunction. (2) The agent never asked how much the caller would pay at all — it stated the invoice's own outstanding total as fact and recorded the full amount as the promised one without the caller ever confirming it, even though the required-fields text still listed "amount" verbatim.

    Neither was caught by the then-249 (then 254) passing tests, because every prompt test checked facts (does the right invoice number appear) or isolated phrases (does "one question per turn" appear somewhere) — never whether a specific branch actually instructed asking for each required field, explicitly, as its own question.

    Fix: rewrote every compact-conjunction branch into explicit sequential asks, and added a test that locks in the requirement directly: test_will_pay_branch_asks_each_required_promise_field_explicitly.

    A prompt is code that produces behaviour exactly like any other code path — a refactor can silently delete a requirement from a paragraph of English as easily as from a line of Python, with no import error, no type error, nothing but a live call to catch it.
    2026-09-16

    Delegating arithmetic to a language model

    Two specialist bugs, same root cause. The promise validator's amount_within_outstanding returned false for a promise of 365,500 against invoices totaling exactly 85,000 + 280,500 — at the limit, not over it; the model's comparison was simply wrong. Separately, the compliance reviewer's rubric only caught a number that was fabricated outright, not one that was stated correctly but summed incorrectly — a call with a misstated total scored qa_score: 1.0, no violation noted.

    Root cause for both: asking an LLM to perform or verify arithmetic. A model that gets 85,000 + 280,500 ≠ 365,500 wrong has no reliable way to also grade whether its own sum is correct — verifying arithmetic is arithmetic.

    Fix: the promise validator split into extraction (LLM: what was said) and validation (pure code: is it complete, future-dated, within balance, a valid method — computed deterministically from the extraction and real invoice data). An arithmetic-consistency check moved into compliance as pure code too, comparing every stated total against the actual sum of outstanding balances — not against anything the model said about itself.

    An LLM can extract facts from unstructured text far better than it can verify a computation over those facts — and it produces a plausible-sounding wrong answer rather than an obvious failure. Wherever a specialist's job includes a deterministic comparison, do the comparison in code and hand the model only the facts and the computed result — never ask it to compute or double-check its own arithmetic.

    More from the failure log

    2026-09-16A dead tunnel produced silence, not an error — an unreachable tool-call webhook fails silently from the caller's perspective, indistinguishable from the agent hanging. Fixed with a pre-call reachability check and a spoken fallback if a tool call times out mid-call.
    2026-09-16The model narrated calling a tool instead of actually calling it — "the tool call succeeded" and "the tool call happened" are not the same claim, and only logging raw webhook requests (not just dispatched ones) can tell them apart.
    2026-09-17A priority-score formula was tested and passing the whole time, and still backwards — the test asserted the exact wrong behaviour, because nothing in the codebase ever supplied real promise history until the step that finally did. "This is tested" and "this has ever run against real data" are different claims.
    2026-09-17A fake test backend that was more permissive than the real one made 200 tests pass while proving nothing about a real header-column bug — a new Sheet column was computed correctly and then silently dropped on write.
    2026-09-17Vapi's call-summary field has never once fired for this project — checked real payloads rather than trusting the documented default, found the whole mechanism marked deprecated, and added a fifth specialist instead of configuring a field that no longer runs.
    2026-09-29Hinglish support was tried twice, failed identically both times on two different models, and was dropped as a scope decision — not a bug waiting for a third rewrite.
